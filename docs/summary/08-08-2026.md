# Project Summary - 2026-08-08

This document summarizes the AWS Terraform infrastructure decisions made through August 8, 2026. It is written as long-term project documentation, not as a transcript.

## Project Overview

- The repository is an AWS infrastructure blueprint managed with Terraform.
- The project supports multiple environments through separate Terraform roots:
  - `environments/dev`
  - `environments/staging`
  - `environments/prod`
- Shared infrastructure is implemented through reusable Terraform modules under `modules/`.
- The project prioritizes security, simplicity, reliability, maintainability, and cost control.

## Goals And Objectives

- Create a reusable Terraform foundation for AWS workloads.
- Keep environment composition explicit and easy to understand.
- Use private networking for application, database, and cache infrastructure.
- Minimize fixed AWS costs where possible without weakening required security.
- Support developer-friendly access patterns for dev without exposing private services publicly.
- Prepare the repository for controlled CI/CD execution through GitHub Actions.
- Maintain useful documentation, diagrams, runbooks, and decision records.

## Technology Stack And Versions

- Terraform: `>= 1.10.0, < 2.0.0`
- AWS provider: `~> 5.80.0`
- AWS services used or planned:
  - Amazon VPC
  - Amazon S3
  - Amazon RDS for PostgreSQL
  - Amazon ElastiCache for Valkey
  - AWS Systems Manager Session Manager
  - AWS Secrets Manager
  - Amazon Route 53
  - AWS IAM and GitHub OIDC
- CI/CD:
  - GitHub Actions
  - Terraform CLI configured in workflow as version `1.10.0`

## Architecture Decisions

- Use one Terraform root module per environment.
- Use reusable modules for cohesive AWS capabilities.
- Split environment files by resource type instead of putting everything in `main.tf`.
- Use provider `default_tags` for standard tags.
- Modules should only set resource-specific tags such as `Name` unless a resource needs explicit extra metadata.
- Use separate public, private services, and private data subnet tiers.
- Place application workloads in services subnets.
- Place PostgreSQL and Valkey in data subnets.
- Keep data subnets private and without NAT routes.
- Use SSM Session Manager for dev database access instead of a public bastion host.
- Add the public subnet tier now, but defer a bastion module until it is explicitly needed.

## Terraform State Decisions

- Use S3 remote state.
- Encrypt state with SSE-S3 instead of SSE-KMS to avoid customer-managed KMS key cost.
- Use Terraform native S3 lock files with `use_lockfile = true`.
- Do not use DynamoDB for Terraform state locking because native S3 lock files are available with Terraform `>= 1.10.0`.
- Keep production and non-production state separated.
- Do not commit Terraform state files, plan files, credentials, or secrets.

## Networking Decisions

- The networking module creates:
  - VPC
  - Public subnets per Availability Zone
  - Private services subnets per Availability Zone
  - Private data subnets per Availability Zone
  - Internet Gateway
  - Public route table
  - Separate services route tables
  - Separate data route tables
  - Optional NAT Gateway routes for services subnets only
  - Optional S3 Gateway VPC Endpoint associated with private route tables
  - Services security group for application workloads
- Dev VPC defaults discussed:
  - Region: `us-east-1`
  - VPC CIDR: `10.10.0.0/16`
  - Two Availability Zones
  - Public subnets:
    - `10.10.0.0/24`
    - `10.10.1.0/24`
  - Private services subnets:
    - `10.10.2.0/24`
    - `10.10.3.0/24`
  - Private data subnets:
    - `10.10.4.0/24`
    - `10.10.5.0/24`
  - NAT Gateway disabled by default for cost control
  - S3 Gateway Endpoint enabled

## Environment Decisions

- `dev` should be low-cost and developer-friendly.
- `staging` should be stronger than dev, but exact sizing and availability settings can continue to evolve.
- `prod` should prioritize reliability, availability, deletion protection, and reviewed deployment controls.
- The same broad architecture applies across environments, with environment-specific sizing and safety defaults.

## RDS PostgreSQL Decisions

- Use a reusable `rds-postgresql` module.
- RDS must be private with `publicly_accessible = false`.
- RDS must use only private data subnets.
- Create a DB subnet group from data subnet IDs.
- Allow PostgreSQL `5432/tcp` only from the services tier security group.
- Store the master password through RDS-managed Secrets Manager integration.
- Do not store database passwords in Git, `terraform.tfvars`, or plain Terraform variables.
- Enable storage encryption using AWS-managed/default encryption instead of customer-managed KMS by default.
- Dev defaults:
  - Instance class: `db.t4g.micro`
  - Storage: 20 GiB gp3
  - Multi-AZ: disabled
  - Backup retention: 1 day
  - Deletion protection: disabled
- Staging defaults:
  - Instance class: `db.t4g.small`
  - Storage: 30 GiB gp3
  - Multi-AZ: disabled
  - Backup retention: 3 days
  - Deletion protection: disabled
- Prod defaults:
  - Instance class: `db.t4g.medium`
  - Storage: 50 GiB gp3
  - Multi-AZ: enabled
  - Backup retention: 7 days
  - Deletion protection: enabled

## Dev Database Access Decisions

- Use a dev-only SSM port-forward helper instead of exposing RDS publicly.
- The helper instance:
  - Runs in a private services subnet.
  - Has no public IP address.
  - Uses Systems Manager Session Manager.
  - Uses the services security group.
  - Can reach PostgreSQL through the private security group rule.
  - Creates SSM interface endpoints for dev because NAT is disabled by default.
- The helper instance type was changed to a Free Tier eligible option after AWS rejected a non-Free Tier type.
- Dev users should retrieve the `postgresql_port_forward_command` Terraform output and connect local tools to `localhost:5432`.

## Cache Decisions

- Use Amazon ElastiCache for Valkey as the Redis-compatible AWS cache option.
- Valkey was selected over Redis OSS because it is open source, Redis-compatible, and aligned with AWS-managed ElastiCache support.
- Use a reusable `elasticache-valkey` module for all environments.
- Valkey must be private and placed only in data subnets.
- Allow Valkey `6379/tcp` only from the services tier security group.
- Enable encryption at rest and in transit.
- Because TLS is enabled, application clients must connect with TLS.
- Do not use Valkey as the only source of truth for business data.
- Dev defaults:
  - Node type: `cache.t4g.micro`
  - Nodes: 1
  - Automatic failover: disabled
  - Multi-AZ: disabled
  - Snapshot retention: 1 day
- Staging defaults:
  - Node type: `cache.t4g.small`
  - Nodes: 1
  - Automatic failover: disabled
  - Multi-AZ: disabled
  - Snapshot retention: 3 days
- Prod defaults:
  - Node type: `cache.t4g.medium`
  - Nodes: 2
  - Automatic failover: enabled
  - Multi-AZ: enabled
  - Snapshot retention: 7 days

## S3 Artifact Repository Decisions

- Create S3-backed artifact repositories only on demand.
- Support private S3 repositories for:
  - Maven artifacts
  - Helm charts
- Do not implement S3-backed npm or NuGet repositories.
- Use AWS CodeArtifact later for npm and NuGet because it has native package manager support.
- Artifact buckets should:
  - Block public access
  - Enable versioning
  - Use SSE-S3 encryption
  - Include lifecycle rules for noncurrent versions
  - Be created only when explicitly enabled by environment variables

## DNS Decisions

- Add an optional Route 53 public hosted zone module for domains bought outside AWS, such as GoDaddy.
- Dev can create the hosted zone on demand.
- The user planned to use `momcorp.net`.
- GoDaddy nameservers must be updated with the Route 53 assigned name servers.
- `dig NS momcorp.net` can be used to verify delegation.
- `api.momcorp.net` was discussed but deferred for later implementation.

## Security Decisions

- Prefer private-by-default infrastructure.
- Do not expose RDS or Valkey to the internet.
- Restrict access with security groups by source tier and port.
- Use SSM Session Manager instead of SSH for dev private access.
- Prefer short-lived AWS credentials and IAM role assumption.
- Use GitHub OIDC for CI/CD AWS credentials instead of long-lived access keys.
- Do not store secrets in Git.
- Use Secrets Manager for the RDS master password.
- Avoid customer-managed KMS keys by default because of fixed KMS cost unless a future security or compliance requirement justifies them.
- Keep Terraform state encrypted and treat it as sensitive.

## CI/CD Decisions

- Add GitHub Actions workflow under `.github/workflows/terraform-deploy.yml`.
- Run the workflow on pushes to `release/deploy`.
- A pull request merge into `release/deploy` is handled because the merge creates a push event.
- Allow manual execution with `workflow_dispatch`.
- Manual inputs:
  - Environment: `dev`, `staging`, or `prod`
  - Action: `plan`, `apply`, or `destroy`
- Automatic push execution defaults to a dev Terraform plan only.
- Apply and destroy are manual-only.
- Destroy uses a saved destroy plan created in the same workflow run.
- Re-run attempts are blocked from executing Terraform steps with `github.run_attempt == 1`.
- The GitHub UI may still show a re-run button, but Terraform execution is skipped on re-run attempts.
- Required GitHub configuration:
  - `AWS_REGION`
  - `AWS_ROLE_ARN_DEV`
  - `AWS_ROLE_ARN_STAGING`
  - `AWS_ROLE_ARN_PROD`
  - GitHub environments for `dev`, `staging`, and `prod`
  - AWS IAM roles trusting GitHub OIDC

## Naming Conventions

- Environment roots are named by environment: `dev`, `staging`, `prod`.
- Module directories are named by capability:
  - `networking`
  - `rds-postgresql`
  - `ssm-port-forward-host`
  - `s3-artifact-repository`
  - `route53-public-zone`
  - `elasticache-valkey`
- Resource names use environment-aware prefixes derived from locals.
- Standard resource tags come from provider `default_tags`.
- Resource-specific `Name` tags are defined inside the owning module.
